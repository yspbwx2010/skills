Every CLI spelling below was checked against `xlings <command> --help` on that binary; behavioural claims come from the source at that commit. **Nothing was built, installed, or updated.**
- **Refresh 2026-09-23**: xlings source `main @ 84572b0` (`VERSION = "2026.9.20.1"`, `src/core/config.cppm:13`), two releases past the stamp above - **2026.9.16.1** (#601) and **2026.9.20.1** (#610). Their changes were read from source, the upstream docs and the merged PRs at that commit and checked against GitHub issue state on 2026-09-23; **no 2026.9.20.1 binary was run** for this pass, so the `--help`-verified claim above covers 2026.9.14.1 only. WARNING: **mcpp 2026.9.21.3 bundles xlings 2026.9.16.1, not 2026.9.20.1** (`kXlingsVersion`, mcpp `src/xlings/xlings.cppm:99`), so an mcpp-provisioned registry does not have the 2026.9.20.1 fixes yet.
- **What changed in 2026.9.16.1 / 2026.9.20.1, in one list** (details and spellings in `references/version-notes.md`):
  - A region object `{"GLOBAL": …, "CN": …}` in `index_repos[].artifact` and `xim.index-base` is now an **ordered candidate chain** (mirror sets the order, not the set): a CN 403 falls to GLOBAL before git. Sub-indexes may declare their own `artifact`. `xlings index list` shows the order (§5.1, §3).
  - Index refresh is **bounded**: git low-speed abort (60 s), index HTTP 10 s connect / 120 s per attempt, 300 s per `xlings update`; overrides `XLINGS_GIT_NETWORK_TIMEOUT` / `XLINGS_INDEX_HTTP_TIMEOUT` / `XLINGS_UPDATE_TIMEOUT` (§5.2).
  - **#582 is fixed** (2026.9.20.1): project-scope installs no longer empty the global shim table (the bug that removed `mcpp`, `gcc`, `cmake` from PATH). A home already damaged is repaired by the next global-scope `install`/`use`, by `self init`, or by `self update` (§9).
  - `interface` now **enforces** each capability's `inputSchema.required` and rejects non-object / invalid JSON `--args` for every capability (`E_INVALID_INPUT`, exit 1, capability not run); `create_subos` / `remove_subos` refuse an empty name - the pair used to wipe every SubOS in the home (§8).
  - The install report reads one per-node outcome record: a **failed** install no longer prints "installed, but 'X' still resolves to …"; `self update` runs `install xlings@latest -y --use`; extraction failures surface as `E_INVALID_INPUT` / `E_DISK_FULL` instead of `E_INTERNAL`.
  - A SubOS `ldd` now answers with the **file's own `PT_INTERP`** for ELF programs carrying one (host and store binaries alike), falling back to the packaged `ldd` only for inputs without one (§1.10).
- **What changed between 2026.8.30.2 and 2026.9.14.1** (`f5a0775` -> `4ea4eac`): seven releases. `references/version-notes.md` is the per-version list of user-visible changes plus the "still broken, do not document as fixed" list — **read it before assuming any behaviour here is the one you remember**.

## 1. Dangerous-misconception corrections (read this section first)

### 1.1 `XLINGS_BIN` has zero read points — unsetting it is hygiene, not a barrier
Neither the xlings nor the mcpp binary **ever reads `XLINGS_BIN`** (zero `getenv` in either tree). It is a pure **output** variable: xlings writes it for the shell, and the shell profile **re-derives** `XLINGS_BIN="$XLINGS_HOME/subos/${XLINGS_ACTIVE_SUBOS:-current}/bin"` from `XLINGS_HOME` + `XLINGS_ACTIVE_SUBOS` [src/core/xself/profile_resources.cppm:87; write points src/core/subos.cpp:1226,1249,1275,1348]. On the mcpp side every hit is in `.github/` workflows; zero in source.
=> **The real isolation set** (when calling `xlings` directly):
`env -u XLINGS_HOME -u MCPP_VENDORED_XLINGS -u XLINGS_PROJECT_DIR -u XLINGS_ACTIVE_SUBOS [-u XLINGS_BIN]` — the last one is pure hygiene. What the three additions do: `MCPP_VENDORED_XLINGS` makes mcpp **copy that binary into the sandbox**, overriding the vendored one [mcpp/src/fallback/xlings_binary.cppm:107]; `XLINGS_PROJECT_DIR` is the **fallback** after CWD walk-up fails and drags an outside project's `mirror`/`workspace`/`index_repos`/`theme` into scope [src/core/config.cpp:785]; `XLINGS_ACTIVE_SUBOS` decides **which subos** install/use/remove land in, outranking the persistent default in `<home>/.xlings.json` [src/core/config.cpp:358,475].
WARNING: the mcpp->xlings hop is already clean (mcpp always passes `env -u XLINGS_PROJECT_DIR XLINGS_HOME=<home>` explicitly [mcpp/src/xlings/xlings.cppm:275-282,1565]); **steps that call xlings directly have no such protection.**

### 1.2 Two paths that stripping the environment does not block
**(a) Copying the user's real `~/.xlings` wholesale by `$HOME`.** mcpp's `copy_xpkg_from_global()` [mcpp/src/fallback/xpkg_copy.cppm:21-41] derives `~/.xlings/data/xpkgs/...` and `~/.xlings/subos/default/data/xpkgs/...` from **`$HOME`/`$USERPROFILE`** and, on a hit, **recursively copies into the sandbox**. The trigger is narrow (`xlings install` exits 0 but the verdir does not exist [mcpp/src/pm/package_fetcher.cppm:1170-1174]), but once it fires **`env -u XLINGS_HOME` is entirely ineffective — it reads `HOME`.** => "never touch the global environment" requires changing `HOME`.
**(b) `.xlings.json` auto-discovery walks up from CWD.** Three brakes [src/core/config.cpp:765-800]: (1) `projectScope: false` -> **skip this file but keep walking up**; (2) a level that has both `.xlings.json` **and** a `subos/` subdirectory is treated as "some xlings home" and **breaks** the walk (the test is literally `is_directory(dir/"subos")`, `:760-763`); (3) only if nothing matched does it fall back to `XLINGS_PROJECT_DIR` (**with the same boundary check**, `:785-798`).
Do not read **`projectScope:false` as a blanket exemption**: `xlings install` (no arguments) has **its own** cwd walk-up [src/cli.cpp:536-599] that reads `json["workspace"]` and installs, **never checking `projectScope`**, skipping only "the level equal to XLINGS_HOME", with **no `subos/` boundary detection**. => For the same `projectScope:false` file, **the `workspace` key still takes effect while `mirror`/`index_repos`/`theme` are unreachable** (`load_project_config_from_dir_` returns at `:641-645`; `mirror` is read at `:653`). The xlings repo root is written exactly this way. => Run gates from a clean CWD, or pass `-g` explicitly.
WARNING, erratum: the comment at `src/core/config.cpp:609-616` claims `projectScope:false` "lets `xlings install` at the repo root still read workspace" — **it describes the separate path in cli.cpp; the comment sits on the wrong function.**

### 1.3 `XLINGS_HOME` is written back unconditionally, and a self-contained layout can silently re-decide the home
`src/main.cpp:65` calls `set_env_variable("XLINGS_HOME", p.homeDir)` on **every run**. => After that line, any `getenv("XLINGS_HOME")` reads **the value xlings computed**; every child process (hook, `os.execute`, shim exec, shell) inherits the resolved value. The source added an `ambient_home_env()` snapshot for exactly this [src/core/config.cpp:18-26] — the conflict guard in `self install` used `getenv` and once **rejected a caller that had explicitly passed `env -u XLINGS_HOME`**. => **`env -u XLINGS_HOME` only affects the outermost resolution.**
Home resolution, four levels [src/core/config.cpp:488-531]: (1) shim owner-anchor override (shims take this path and **ignore the environment**) > (2) `$XLINGS_HOME` > (3) **self-contained detection** > (4) `$HOME/.xlings`.
Level (3) is the easiest trap after stripping the environment: the test is whether **the parent of the binary's directory** (the `<root>` of `<root>/bin/xlings`) has both `.xlings.json` and `bin/xlings`; on a hit the home **silently becomes that root** (on Windows the json must additionally carry both `version` and `activeSubos`, otherwise a subos directory false-matches).
WARNING: with **both** `HOME` and `XLINGS_HOME` stripped, on Linux the home becomes **`./.xlings` (relative to cwd)**.

### 1.4 "mirror" is two unrelated mechanisms, and it does not switch the way you expect
| | **A. Regional mirror CN/GLOBAL** | **B. GitHub proxy fallback** |
|---|---|---|
| config key / env | `mirror`; `XLINGS_*_MIRROR` (**install time only**) | `mirror_fallback`; `XLINGS_MIRROR_FALLBACK` |
| values | bare string `"GLOBAL"`/`"CN"` (mcpp also writes `"auto"`) | `auto` (default)/`off`/`force` |
| code | `src/core/config.cpp` (`Config::mirror_`) | **`src/core/mirror/`** |
| effect | picks index repo URL + resource server | rewrites github.com hostnames (ghfast/ghproxy/kkgithub/jsdelivr) |

The directory name `src/core/mirror/` refers to **B**; the `"mirror"` key in `.xlings.json` belongs to **A**, and **its code is not in that directory at all**. Do not confuse them.
**`xlings config --mirror` performs zero validation**: the value is collected and written verbatim [src/cli.cpp:729-743], so `--mirror foo` gets written. **`--lang` is unvalidated in exactly the same way** [src/cli.cpp:712-726, the same shape byte for byte — `xlings config --lang bogus` -> `lang = bogus`, exit 0], so the silent-fallback trap below applies to `lang` too. Only **omitting the value**, which goes through the interactive selector, restricts them to `{GLOBAL, CN}` / `{auto, en, zh}`; compare `--ui-mode`/`--theme`/`--interactive`, which all have `diag::emit` + `return 2` rejection branches [`:770`, `:840`, `:868`].
**Runtime matching is exact and case-sensitive**: `Config` reads without normalizing [src/core/config.cpp:545-546,653-654]; only `self install` trims and uppercases before writing [src/core/xself/install.cpp:34-41 `normalize_mirror_`]. Writing `"mirror": "cn"` -> lookup of `"cn"` misses the builtin table (which only has `"CN"`) -> lookup of `"DEFAULT"` misses -> falls back to GLOBAL, **silently going back to github**.
WARNING: **the upstream schema doc's worked example is exactly the lowercase form** (`docs/spec/xlings-json-schema.md:518` writes `"mirror": "cn"`). That example is self-consistent (it also lowercases the `XLINGS_RES` key at `:533`), so **copying half of it is what bites**. **Do not copy that passage from upstream docs.**
**`XLINGS_MIRROR`/`XLINGS_INSTALL_MIRROR`/`XLINGS_RELEASE_MIRROR` have zero runtime readers** — they are only used by `xlings self install` to **write into** `.xlings.json` [src/core/xself/install.cpp:57-64 `env_install_mirror_`]. => **"set an env var to temporarily switch mirror" is impossible in xlings**; change the config or run `xlings config --mirror`.

### 1.5 Three classes of "that command does not exist"
- **`xlings subos fork` does not exist.** The full subos subcommand set is `new`/`use`/`list`(ls)/`remove`(rm)/`info`(i)/`stop`/`runtime` [src/cli/spec.cpp:42-50]; forking is the **option** `subos new <name> --from <SOURCE>`. There is also no `subos exec` and no `subos shell`.
- **The five short aliases `xim`/`xvm`/`xself`/`xsubos`/`xinstall` were removed wholesale in 0.4.8** [src/core/compact/xself.cppm:85 `LEGACY_ALIAS_NAMES`]. Invoking via an alias argv[0] prints ``[error] `xim` was removed in 0.4.8. Use `...` instead.`` and **exits 2** [compact/xself.cpp:76-84; the exit code itself is src/main.cpp:45-46]. Leftover symlinks are actively cleaned by `self init`/`self doctor --fix`; e2e locks this in `cli_short_alias_removal_test.sh`.
- **`xlings help` is not a command**: it is not among `spec::root()`'s children => `[error] unknown command: help`, **exit 1**. Use `xlings --help` / `-h` / bare `xlings`.

### 1.6 `--agent` is not enough to make `remove` safe; pass `-y` explicitly
Non-interactive confirmation has **two strategies** [docs/spec/diagnostics.md:96-108]: `Proceed` (default "continue", install/update) and **`Refuse`** (default "do nothing", remove) — the latter reports `Diagnostic{Error}` and **exits 2** rather than faking success. The distinction came from a real defect: `--agent` answers every prompt with `defaultValue`, and the two confirmations have opposite defaults, so **`xlings remove foo --agent` once printed `cancelled`, exited 0, and left the package installed**, which the calling agent read as "removal succeeded". => **In scripts and agents, always pass `--yes` explicitly to install/remove/update.**
WARNING: `remove --force` and `-y` **are separate**: `-y` says "do not ask me"; "break the dependency chain" is a different decision, and a scripted `remove -y` should still be stopped by it [src/cli.cpp:1718-1722].
`--force` now covers **three** situations, not one: a package others depend on, **a recipe no index can resolve any more**, and **an `uninstall()` hook that throws** [spec.cpp:26]. In the last two cases the state (version record, workspace binding, shim, payload) is rolled back either way; without `--force` the command also emits `xim.uninstall_hook_failed` and **returns 1**, with `--force` it returns 0 [src/core/xim/commands.cpp:1181-1223]. What `--force` still does **not** do is override the detach-only decision — if another subos still references the payload you get a detach, never a delete [src/core/xim/installer.cppm:568-596]. Do not sell it as "delete it for real".

### 1.7 "An `$MCPP_HOME` cannot be relocated wholesale" — conclusion kept, but `--fix` is no longer destructive about it
| Layer | After copy/move | `doctor --fix` |
|---|---|---|
| version database | **relocatable**: stores `${XLINGS_HOME}`/`${XLINGS_DYNAMIC_SUBOS_DIR}` **placeholders** [src/core/xvm/db.cpp:666-670; db.cppm:303-304] | not needed |
| absolute store paths in records / index caches / subos manifests | recorded under the **old** root | **yes, since 2026.9.5.1** — re-pointed to the current root |
| sysroot links in every subos | point into the old root | **yes, since 2026.9.5.1** |
| `subos_info` block | missing/stale -> D1 "SubOS does not describe itself" + `host_glibc` mismatch | yes, see below |
| **ELF** in the payload | `PT_INTERP`/`DT_RPATH`/linker scripts still point at the **original absolute paths** | **no, and it says so in a note** |
| subos paths inside alias/envs | `SubosPathBaked` warning | yes, `pin_subos_paths` rewrites them to placeholders [db.cpp:666-670] |

- **Since 2026.9.5.1 a moved home is diagnosed as one finding, not hundreds of symptoms**: `FindingKind::HomeRelocated` [src/core/xself/doctor.cppm:174] reports `home relocated  this home is at <new>, but its records were written for <old>`. The detector takes the **modal** store prefix, never the longest common prefix, and the destructive repairs (dropping a registration, deleting a sysroot link) now ask **"is this payload present under the current root"** instead of "does the recorded path exist" [src/core/xvm/relocation.cppm]. An old root that is still a live independent home does not count as a move.
- WARNING, version floor: **2026.9.4.1 is strictly worse than 2026.8.30.2 on a moved home** — it deletes the dangling links the old symlink workaround could recover (upstream measured: 1173 sysroot links deleted and 367 registrations dropped on a 152 GB moved home whose 234 package directories were all present). On that exact version, keep a symlink at the old path and **do not run `--fix`**. From 2026.9.5.1 the same home loses only what an un-moved home would.
- A registration dropped by an older client needs **no download** to recover: `xlings install <pkg>@<version>` re-registers and replays the links in about a second when the payload is still on disk.
- ELF embedding **does not happen in the package script**: the install hook only "flips a switch", and after the hook the xlings installer calls `executor.apply_elfpatch_auto()` centrally [src/core/xim/installer.cpp:3246]; the tool is libxpkg's elfpatch, which underneath uses **the patchelf inside the payload** (different versions extend the dynamic segment differently).
- **`doctor --fix` never re-patches ELF** (`grep -c patchelf src/core/xself/doctor.cpp` gives **0**). The payload-level remedy is **`xlings install <coordinate>` reinstall** [doctor.cpp:1811], which re-runs elfpatch — **that is the real mechanism behind "ELF got rescued after relocation"**, and it needs network and time.
- **Full chain of "copied home errors on first use, one `doctor --fix` repairs it"** (observed on a copied home used for an isolated packaging run): (1) the copied subos lacks the `subos_info` block -> **D1 = "SubOS does not describe itself"**; (2) `host_glibc` is missing or is the source machine's old value, and `closure_check` compares it against the glibc payload owning the interpreter -> **"glibc version mismatch"**; (3) `--fix` calls `describe_block`, where `runtime` reaches level 4 and **infers the binding by measuring the `lib/libc.so.6` symlink** [src/core/subos/manifest.cpp:381-420], while `host_glibc` is re-stamped from the current host via `platform::host_glibc_version()` — both inconsistencies disappear at once. => **What gets rescued is the bookkeeping, not the ELF.** While the original paths still exist the binaries still run (using the old home's loader — a latent hazard); once the original paths are gone you get `BrokenPayload` -> reinstall.
=> **Operational conclusion unchanged: install fresh in place, do not `mv`.** Upstream calls relocation won't-do for the same reason (`PT_INTERP` is read literally by the kernel); a registry-shaped home is a rebuildable cache, so the supported recovery is to drop it and re-provision. What changed is only that a moved home is now survivable rather than destroyed on the next `--fix`. [field-tested: `ls` shows the file, `exec` reports it does not exist]

### 1.8 `xlings use <name>` without a version **never auto-switches on candidate count** (three upstream texts state the opposite)
Evidence: the implementation says `// NO single-candidate auto-switch.` [src/core/xvm/commands.cpp:1079] — that comment rules out switching because the count happens to be 1, not switching after a question. `cmd_use_by_name` (`:1075`) falls through to `return cmd_list_versions(...)` (`:1140`), which always `return 0` (`:1072`). **No candidate count auto-switches**, and the exit code for `>1` is **0, not 2**.
CARVE-OUT: with `tui.interactive` on (`xlings config --interactive true`) **and** a frontend that can be asked, `:1112 if (!all && stream.interactive())` emits a `PromptEvent::Kind::Select` and, on `Chosen`, calls `cmd_use(target, c.value, …)` and returns its rc (`:1127`, `:1137`) — so the bare `use <name>` really does switch there. With the default (interactive off) or nobody to ask, `NobodyToAsk` falls through to the panel (`:1135`) and it lists. See §6.
There is also **no `--pick`/`-i`** (`spec.cpp:38-39` has only `-a/--all` and `--strict`).

### 1.9 A shim can now hand the name back to the host PATH and exit 0 (2026.9.3.1)
A name can sit in `<home>/subos/<n>/bin/` purely because some **project** declared it — a project's own bin is never on PATH, so its command names have to live in the directory that is. When the resolved scope makes **no claim at all** on the name (not active, and not even present in `installed[]`), the shim no longer errors: it finds the first same-named executable that belongs to **no** xlings home and `exec`s it, printing `name: no version in subos 'X'; running /usr/bin/name` on **stderr only when stderr is a tty** [src/core/xvm/shim.cpp:596-625, helpers `:408,471,516,528`].
**Only that branch passes through.** "In `installed[]` but nothing active" and "pinned to a version that is not installed" are claims this scope makes and cannot meet; both stay errors, deliberately, rather than becoming the silent substitution pyenv ships. A shim invoked by explicit path (`<project>/.xlings/subos/_/bin/node`) never passes through either.
=> **For a hermetic toolchain this is a real hazard**: a tool missing from your home used to fail loudly and now quietly runs the host's build of it, so a gate can go green on the wrong binary. In non-interactive gates the notice is not even printed. **Check provenance, not just the exit code** — e.g. assert that `command -v <tool>` resolves under your own home.

### 1.10 `ldd` inside a SubOS answers with the file's own loader (2026.9.20.1)
A SubOS `bin/` sits first on PATH, so its `ldd` answers every script that calls `ldd`. Up to 2026.9.16.1 that was the packaged glibc `ldd`, which picks a loader from its own `RTLDLIST` and ignores the `PT_INTERP` the file was linked for: on a host whose binaries use `DT_RELR` it rejected every host binary (#608), and elsewhere it reported every host library `not found` **and exited 0**, so `set -e` / `pipefail` did not catch it and bundling scripts shipped empty bundles. Now the `ldd` shim runs the file's **`PT_INTERP`** with `LD_TRACE_LOADED_OBJECTS=1` whenever the argument is an ELF file that has one; `-d`/`-r`/`-u`/`-v` are translated into loader environment the way glibc's own `ldd` does (`LD_WARN`, `LD_BIND_NOW`, `LD_DEBUG=unused`, `LD_VERBOSE`), and everything else - no argument, `--version`/`--help`, several files, non-ELF, static, a shared library without `PT_INTERP` - falls through to the packaged script. Upstream verified the output byte-identical to `/usr/bin/ldd` for host binaries.
=> On a client older than 2026.9.20.1, **do not trust `ldd` inside a SubOS for host binaries**; call the host's `/usr/bin/ldd` by path. Separately, historic `glibc@2.39` payloads installed by pre-libxpkg-0.0.51 clients carry a corrupted `ldd` script (`RTLDLIST` mangled); a reinstall of the package repairs it, and a fresh install from the current index is correct.

## 2. Mental model

```
$XLINGS_HOME/                      resolution: 1 shim owner anchor > 2 $XLINGS_HOME > 3 self-contained > 4 $HOME/.xlings
├── .xlings.json                   global config + versions (version DB) + subos registry, all in one file
├── .xlings.lock(.owner)           home-level state lock + owner sidecar
├── bin/                           shim landing (a shim is a hard link to xlings itself, dispatching on argv[0])
├── data/xpkgs/<ns>-x-<name>/<ver>/  the one and only payload landing site
├── data/trash/                    staging when removal fails; MUST be a sibling of xpkgs
├── data/runtimedir/               download cache; archives now STAY here (§10, and config-layout.md §3), plus .stage/<key>-<pid>/
├── data/xim-pkgindex/             default index (constant directory name, not an array subscript)
├── data/xim-pkgindex-local/       local recipe overlay (`config --add-xpkg`), listable and clearable since 2026.9.12.1
├── data/<name>/                   other index_repos entries; directory name = entry name
└── subos/{current -> default, <name>/{.xlings.json, bin, lib, usr, generations}}

<project>/.xlings.json             project manifest (user-written, 12 keys, see 4.2)
<project>/.xlings/{.xlings.json, data/, subos/<name>/ or subos/_/}   project state (xlings-written)
```

- **Three spellings of a package coordinate must be kept apart** (`src/core/xvm/db.cppm:36` exists to provide `display_coordinate`): command line `<ns>:<name>@<ver>` (ns first, `local:mcpp@0.0.27`) / storage directory `<ns>-x-<name>/<ver>` (**the version directory name carries no ns**, `local-x-mcpp/0.0.27`) / version DB key target -> `"<ns>:<ver>"` (**ns rides on the version**, `mcpp` -> `local:0.0.27`). Formatting the DB straight as `{}@{}` produces `mcpp@local:0.0.27` — which looks like a version named `local:0.0.27`, **and really does parse that way**, then resolves to nothing. `::` is normalized to `:` at the very start of parsing, so `xim::gcc` is equivalent to `xim:gcc`.
  **Whether a version key carries the `ns:` prefix is a contract, not an accident** (`docs/spec/xlings-json-schema.md:70-85`, since 2026.9.2.1): packages from the index **named `xim`** get a bare key, everything else gets the prefix, and the decision looks at the **entry's name, never its position in `index_repos`** — reordering the array no longer re-keys installed packages. A key's spelling is fixed at first write and reused on reinstall/repair. Reads are tolerant both ways (`xim:2.1.222` finds a record stored as `2.1.222`), but `ns:v` never matches `other:v`. Both spellings of one version with the same `path` are **one registration written twice**; doctor reports `duplicate version key` and `--fix` merges them across every subos [src/core/xvm/db.cppm:120-166].
- **SubOS has three isolation tiers on two orthogonal axes** (V4 hard rule [src/core/subos.cpp:1264-1276]): shell tier (default `subos use <n>`, no root, **no filesystem isolation**, only PATH swap + env injection) / FS tier (`--sandbox [bwrap|proot]`, no root, separate filesystem view on Linux) / image tier (`subos new --storage image` then `use --sandbox`, **requires root**). Storage mode (shared/tmpfs/image) **only takes effect on the `--sandbox` path**; the shell-level entry **never mounts**.
  WARNING: **`--sandbox` on macOS/Windows is not a security boundary** — it only redirects HOME/USERPROFILE and isolates neither the host filesystem nor processes [README.md:44-48]. **Use an OS sandbox or a VM for untrusted code.**
- **"Is it installed" has no single DB; there are three sources**, and the source explicitly records that they have historically disagreed (four simultaneously inconsistent answers on one real machine with 124 packages) [src/core/xim/install_state.cppm:10-34]: A the `versions` ledger, B each subos's own `workspace`, C the payload stamp `.xpkg-install.json`. The sole arbiter `installation_state()` is tri-state `Absent`/`Installed`/`Incomplete` and **deliberately demands positive evidence**: on a real machine, 115 of 340 payloads had "payload but no ledger", mostly residue superseded by a newer version rather than broken installs, and a naive rule would have drowned 29 real problems [`:99-116`]. => **Do not stat directories to decide "is it installed"; ask `xlings list` / `interface list_packages`.**

## 3. Command surface

**The CLI has a single source of truth**: `root()` in `src/cli/spec.cpp`, pinned by a **bidirectional parity test** (`tests/scripts/test_cli_spec_parity.py`: forward = every (command path, option) the spec publishes must parse in the real process; reverse = every option literal in the hand-written argv loops must exist in the spec). => **Copy from it**; do not reassemble from scattered help text. Per-flag tables in `references/commands.md`.
**16 top-level commands**: `install remove update search list info why use config subos self script interface index agent profile` (count re-checked against `xlings --command-reference-json` on 2026.9.14.1). **Global options** (`global=true`, legal on **every** command, ignored where inapplicable): `-y/--yes`, `--agent`, `-v/--verbose`, `-q/--quiet`, `--ui-mode <cli|tui|auto>` — **with one exception: `-y/--yes` must come AFTER the subcommand for every positionally dispatched command — `subos`/`self`/`profile`/`index`/`script`/`agent`.** It is the one global the strip loop does not filter [src/cli.cpp:1400-1403], so it survives into the argv those handlers read positionally and `xlings -y subos list` exits **2** with ``unknown subcommand for `xlings subos`: subos``, while `xlings subos list -y` exits 0. On `script` and `agent` the failure is **1**, not 2, and does not even name the real problem: they never reach `spec::validate_manual_argv` (`agent` dispatches at `:1457`, before the validate blocks at `:1531`/`:1562`), so `xlings -y script` reads `fargv[2]` as the filename [`:1598`] -> `[error] failed to load script: package file not found: script`, and `xlings -y agent` reads `argv[2]` as the subcommand [src/agent/agent.cpp:63] -> `Unknown: xlings agent agent` [both measured, 2026.9.14.1]. Matters because this skill also tells you to always pass `--yes` (1.6).
WARNING: **`-h/--help` and `--version` are not global** — they are commands in their own right; accepting them mid-line would make `xlings subos new foo --version` silently create a subos [src/cli/spec.cppm:16-24].

On `config`, `2` is ambiguous between `Refuse` and a rejected/omitted enum value — read the diagnostic.
`docs/spec/diagnostics.md:69-84`: **"severity says how bad this is, the exit code says what happened, and the two may disagree"** — when a project declares an uninstalled version, the shim reports `Warn` but **still exits 1**; the criterion is **who can fix it**.

## 4. Configuration

### 4.1 Global `<home>/.xlings.json`
One file carries **three** kinds of thing at once: user preferences + **the installed-version database (`versions`)** + **the subos registry**. Common keys: `activeSubos`/`mirror`/`lang`/`uiMode`/`theme`/`tui.interactive`/`versions`/`index_repos`/`xim.index-repo`/`xim.mirrors.index-repo.<REGION>`/`xim.index-base`/`XLINGS_RES`/`hintsSeen`/`version`/`verifiedBy`/`knownProjects`/`subos`. Per-field table in `references/config-layout.md`.
WARNING: **`XLINGS_RES` is not an environment variable**; it is a JSON key (plus a sentinel string in package recipes). The keys `repo` and `need_update` are **written but never read** (zero readers in `src/`).
**Two keys added since the previous baseline** — `knownProjects` in 2026.9.3.1, `verifiedBy` in 2026.9.12.1: `verifiedBy` = the client version of the last `self doctor --fix` that converged with nothing outstanding (distinct from `version`, which moves on every `self install`/`upgrade` whether or not anything was ever checked); `knownProjects` = absolute paths of projects that have installed in project scope, **paths only** — command names are recomputed from each project's own state file whenever the shim table is rebuilt, so a cached list cannot go stale [src/core/config.cppm:400-404,607-613].
**Writes fall into three classes** (it was two at the previous baseline; full enumeration in `references/config-layout.md §1`): `xlings config --*`, repo add/remove, `index use`, subos add/remove/modify, and `self migrate` go through a **locked read-modify-write** (`<home>/.xlings.lock`, **collect-then-replay**: edits are collected first, then replayed onto a document **re-read under the state lock** — replaying onto the copy read earlier would write every other key back as it looked before some concurrent install). Since 2026.9.12.1 the three near-every-command writers (`record_client_version` / `record_verified_version` / `mark_hint_seen`) also go through the state lock, but with a **2-second timeout and a silent skip** — a lost hint is an inconvenience, a lost `versions` entry is not [src/core/config.cpp:1320,1370-1426]. `save_versions()` still writes directly, relying on its caller to hold the lock.
=> **A read-only-looking command can still write this file.** On a read-only home the write now fails as an error rather than aborting the process, but if you check a working tree for cleanliness, expect `.xlings.json` to change after commands that only read.

### 4.2 Project `.xlings.json`
**The parser recognizes only 12 keys**: `projectScope`/`mirror`/`lang`/`uiMode`/`theme`/`tui.interactive`/`workspace`/`index_repos`/`XLINGS_RES`/`xim.index-base`/`subos` (the old name `projectSubos` is still recognized)/`versions`. **There is no `deps`, no `toolchain`, no `index`.**
WARNING: the upstream schema doc's project field table **omits `versions` and `xim.index-base`**, and its global table omits `subos`/`repo`/`need_update`/`verifiedBy`/`knownProjects` (`docs/spec/xlings-json-schema.md:240-251`). **Do not treat it as a complete list.**
- **Triggering project mode auto-activates the project SubOS, independently of `workspace`**: with a `subos` name -> Named (`<proj>/.xlings/subos/<name>`); **otherwise always Anonymous** (`<proj>/.xlings/subos/_`). Any claim that "auto-activation requires a workspace declaration" states the condition too narrowly and misleads people into thinking they are not isolated without a workspace.
- `index_repos` **replaces** the global list rather than merging; `effective_data_dir()` switches to the project data directory **only when the project declares `index_repos`**.
- `workspace` merge order: Named = project manifest <- project subos file; Anonymous = global <- project manifest <- project subos file. But **the write target is `projectSubosWorkspace_` in both modes**, so **saving always writes only the subos-side file**; a hand-written project manifest is read-only as far as `save_workspace` is concerned.

### 4.3 The two most commonly misjudged semantics (details in `references/config-layout.md`)
- **`envs` has only two ops, and `set` does not "set"**: `set` = export **only if the variable does not exist** (if it exists, **even with an empty value**, it is left alone); `prepend` = prefix concatenation. **An empty value counts as set, and the user's value wins.** This name has already fooled the reporter of `xim-pkgindex#565` and the author of `xlings#508`; renaming it would make the new op fail at install time with `EnvDeclMalformed` on every already-released older client, so **the name stays and the semantics live only in the docs**. Values must use the placeholders `${pkgdir}`/`${subosdir}`/`${home}`/`${xlings_home}`.
- **An absent `subos_info.runtime` is a "known unknown", not a default** (tri-state: no block / block without a `runtime` key = "we looked and cannot say" / well-formed; when present it must be `<name>@<version>`, and **the empty string is invalid**). => **Downstream that reads an absent value should degrade and explain why, not pick a default on its behalf.** Also: **declaration beats index** (SubOS declaration > the version already active in this subos > index resolution), and **an index update never changes an existing SubOS's binding**; `latest` and "the largest entry in the table" are two different questions (the index has `musl` `latest = 1.2.5` while the table contains `1.2.6`).

## 5. Mirrors and networking

(The two mechanisms are distinguished in 1.4; full tables in `references/config-layout.md`.)

### 5.1 Regional mirror A
Priority chain: `""` (default, equivalent to GLOBAL) < global `mirror` < project `mirror` < **explicit caller argument** (highest; used internally to force a cross-region fallback). Hostnames: resource server GLOBAL `github.com/xlings-res` / CN **`gitcode.com/xlings-res`**; default index repo GLOBAL `github.com/openxlings/xim-pkgindex.git` / CN **`gitee.com/sunrisepeak/xim-pkgindex.git`**. WARNING: **the two CN hosts are not the same operator** — the index comes from gitee, the resources from gitcode.
**mirror does not rewrite the index repo git URL** — `sync_repo_url_` is the identity function with a `[[maybe_unused]]` parameter [src/core/xim/repo.cpp:148-151]; the regional difference is already consumed **during config resolution**.
**A region object is an ordered chain, not a pick (2026.9.16.1, #598)**: wherever the config holds `{"GLOBAL": …, "CN": …}` - `index_repos[].artifact`, `xim.index-base`, and a sub-index's `["artifact"]` in `xim-indexrepos.lua` - it is read as `mirror`'s region first, then GLOBAL, then the rest in declaration order [`parse_region_chain`, src/core/config.cpp:30]. A failed pointer or asset fetch (403, 429, offline) moves to the next base; **git is reached only after the whole chain fails**. Before, the object collapsed to one base, so a GitCode 403 under `mirror = CN` turned straight into a GitHub `git clone` - the very connection the CN setting avoids. Pointer file names are derived per base (`<last path segment>-pointers.json`), so mirrors should keep the same repository name. Exceptions: `xim.mirrors.index-repo` and the git URLs in `xim-indexrepos.lua` take **only the first** entry, because they name a git remote and a clone has one origin. An `xim.index-base` chain that is exhausted never falls back to the official server.
**Cross-region append**: after a region is chosen, the servers of **all other regions** are appended as candidates too (rationale: both hosts mirror the same set of releases, and treating them as partitions is precisely what turns "mirror sync lag" into "downtime"), then the primary is chosen by TCP latency probing (2000ms timeout, adopted immediately at <=100ms, **cached in-process only**).
**Probing happens at install time; zero probing at runtime**: `self install` probes `github.com` vs `gitcode.com` (1000ms timeout; CN wins iff gitcode is reachable **and** (github is unreachable **or** slower by more than 20ms)). WARNING: it probes **the resource host, not the index host** — an earlier version probed gitee (the CN index host), but on some links gitee is rate-limited while gitcode is fine, so it wrongly kept GLOBAL and every subsequent download stalled on unreachable github.

### 5.2 Proxy fallback B and adaptive
Builtin table jsdelivr (raw only, 50MB)/ghfast/ghproxy-net/kkgithub, with three rewrite shapes Prefix/HostReplace/JsDelivr; a user override at `<data>/github-mirrors.json` **replaces the whole table rather than merging**.
**Non-github hostnames are never proxied** => the gitcode/gitee URLs CN users get have **no fallback at all**.
**Adaptive is gated on sha256**: with sha256 -> everything is ordered by latency and **a third-party mirror can outrank the author-declared URL** (the bytes are locked by the hash); without sha256 -> the author URL is pinned at position 0, **but the pin fails if its host is unreachable or has been penalized (infinite)**. The penalty is **session-scoped**, never persisted to disk, and re-probed on every invocation.
**Index fetching deliberately does not apply the github proxies**: those proxies are frequently TCP-reachable while not actually serving assets, and one falsely-alive proxy ranked first costs roughly 30s of timeout per dead host — **this is the main cause of CN users hanging at "fetching package index"** [docs/design/index-distribution.md:111-113]. The index path instead **unconditionally appends the GLOBAL server**.
**Every network step of an index refresh is bounded (2026.9.16.1, #599)** [docs/design/index-distribution.md §4ter; docs/spec/xlings-json-schema.md]:

| Step | Bound | Override |
|---|---|---|
| git transport | `GIT_HTTP_LOW_SPEED_LIMIT=1000` + `GIT_HTTP_LOW_SPEED_TIME=60`, and `GIT_TERMINAL_PROMPT=0` | `XLINGS_GIT_NETWORK_TIMEOUT=<sec>\|off`; values the operator already set are **not** overwritten [src/core/compact/git.cppm:131-140] |
| index HTTP | 10 s connect, 120 s per attempt | `XLINGS_INDEX_HTTP_TIMEOUT=<connect>:<max>\|off` [src/core/xim/indexfetch.cpp:54-57] |
| HTTP stall | window average below 10 KB/s for 15 s -> next candidate | `XLINGS_DOWNLOAD_LOW_SPEED=off\|<bytes>:<secs>` (older) |
| one `xlings update` | 300 s total; remaining sources are **skipped and reported**, keeping their local copy | `XLINGS_UPDATE_TIMEOUT=<sec>\|off` [src/core/xim/repo.cpp:630-656] |

The measured motivation was an 11.5-minute stall: the 3 s TCP pre-probe passed, the handshake completed, and git then waited on a silent peer. => A slow link now yields `[index] 300s refresh budget reached: N source(s) were not refreshed and keep their local copy` - **read that warning rather than trusting the exit status alone**, and raise the budget explicitly instead of retrying.

### 5.3 Index repos: #575 "entries are peers", and the upgrade trap
**Post-change core invariant: directory, namespace and pointer key all come from the same place, `repo.name`.** Array position **no longer carries any privilege** (before the change, `main_repo_dir()` took the default index at subscript 0, and the artifact authorization gate was a **URL substring match compiled into C++**, which every official **sub**-index URL also passed because it shared the prefix). Artifact eligibility is now a **pure configuration question**: the entry declares `artifact` itself, or its `url` equals the declared source for that name. URL comparison is normalized (trailing `/` and trailing `.git` stripped) but **deliberately leaves scheme/host alone** (treating a gitee copy as the same repo as github is exactly the conflation this change removes).
**Upgrade trap (must read)**: a polluted directory contains the whole official index, including the `xlings` package itself, so `xlings self update` (= `xlings install xlings@latest`) **is blocked by its own ambiguity**. Two escape hatches:
```bash
xlings install xim:xlings@latest -y                  # explicit namespace, bypasses ambiguity (recommended)
rm -rf <home>/data/<name> && xlings self update      # or delete the polluted directory
```
Once upgraded, **a single `xlings update` repairs it automatically** (the polluted directory now qualifies for "take its own artifact", and the whole tree is replaced atomically). WARNING: a self-hosted fork under the same name **gets no artifact acceleration after the change and falls back to git** (its URL does not match the declared source) — to get acceleration, write your own `artifact` key.

### 5.4 The local recipe overlay is now a lifecycle, not a write-only hole (2026.9.12.1)
`config --add-xpkg <FILE>` writes into `<global data dir>/xim-pkgindex-local`. Until 2026.9.12.1 nothing could read that directory back out. Three verbs now can [spec.cpp:40; `src/core/xim/overlay.cppm`, `src/core/xim/commands.cpp:2335,2377,2409`]:
```bash
xlings config --list-xpkg              # name / version / status / source
xlings config --remove-xpkg <NAME>
xlings config --clear-xpkg stale       # stale = identical + behind + missing
xlings config --clear-xpkg all
```
`status` is one of `unique` / `identical` / `modified` / `behind` / `missing` [overlay.cppm:63-71]. Provenance lives in `.overlay.json` next to the recipes; a recipe added by an older client has no record and shows up as `source = untracked` after a file scan. An illegal `--clear-xpkg` category **exits 2**.
**Two behaviour changes come with it, both of which delete files:**
- `--add-xpkg` **refuses to store** a recipe byte-identical to the already-synced index (Note `xim.overlay_identical`, exit 0, nothing written) [commands.cpp:2259].
- `xlings update` **garbage-collects** overlay recipes that have become byte-identical to the freshly synced index, prints which ones, and rebuilds the catalog again [commands.cpp:2477-2490].
=> **`xlings update` is no longer a read-only sync.** Do not treat the overlay as version control for a recipe you maintain: the moment it matches upstream byte-for-byte it disappears. A genuinely divergent (`modified`) recipe is untouched.
=> Every bare-name shadow in the overlay makes resolution fall through namespace priority and print a notice, so `--list-xpkg` then `--clear-xpkg stale` is worth doing once on any home that has been used for recipe experiments.

## 6. Multi-version and `use`

- Physical storage keeps `<ns>-x-<pkg>/<ver>/` side by side with **reference-counted sharing**; each subos picks its own active version. `xlings use gcc 14.2.0` is equivalent to `xlings use gcc@14.2.0`.
- **Switching is per release group**: since gcc ships `gcc`/`g++`/`cpp` together, they switch together. **Programs missing from the new release are named individually** and keep pointing at the old release; `--strict` instead **refuses to switch and changes nothing**.
- **Without a version: no candidate count switches.** 1 candidate -> **list, do not switch, exit 0**; >1 -> list + tip, no changes, **exit 0**; 0 -> error (including what to install), exit 1. "Omitting the version was never an expression of intent to switch; it is a question", and **"is there a human at the keyboard" cannot be detected** (many agents allocate a pty). The reason single-candidate auto-switch was withdrawn [src/core/xvm/commands.cpp:1079-1098]: the candidate set is "versions opted into **in this subos**", not "versions I have installed", and the user cannot see that number — on a real machine `use gcc --all` listed five while `use gcc` silently wrote state. "It traded certainty of **semantics** for certainty of **outcome**."
  **Three upstream texts state the opposite; do not copy them**: the header comment at `src/core/xvm/commands.cppm`, `docs/quick-start/multi-version.md:52-56`, and older behaviour tables all say "1 candidate -> switch directly". **The implementation is authoritative.**
- **A picker exists in another form**: when `if (!all && stream.interactive())`, a `PromptEvent::Select` is emitted **automatically** [commands.cpp:1112]; the switch is the **persistent config** `xlings config --interactive true`, not a command-line flag; and it **does not fail loudly** — the `NobodyToAsk` branch is **empty**, silently falling back to the listing [`:1135`].
- **`use` only switches among versions already installed in this subos**; a fresh subos refuses even if the version is installed elsewhere and tells you to `install`. Rationale: **the version database records no dependency relations**, so activating directly would activate gcc alone and not the glibc it depends on, yielding a toolchain that runs, reports the right `-print-sysroot`, **and only fails to compile**, with no warning anywhere. `--all` widens the candidate set to all subos (**for viewing only**; it does not change this rule).

## 7. SubOS lifecycle and doctor

```bash
xlings subos new dev --storage shared|tmpfs|image [--image-size 50G] \
                     [--from <local subos name | subos:py-ds@1.0.0>] [--runtime glibc@2.39]
xlings subos use dev [--sandbox [bwrap|proot]] [--cmd "…"] [--global] \
                     [--shell sh|bash|zsh|fish|pwsh] [--keep|--no-keep|--ttl <sec>] [--gpu]
xlings subos list|info|stop|remove ;  xlings subos runtime glibc@2.39 [name]
```
- `--from` containing `:` or `@` -> treated as a pkg-spec (the base xpkg is installed automatically if missing); a bare name -> **fork a local subos**. That is what "fork" means here. `--runtime` is a **creation-time** attribute (changing it afterwards invalidates every installed payload).
- `--cmd` runs one command non-interactively and **exits with that command's exit code**; available at both shell and sandbox tiers. `--shell <kind>` prints activation code to stdout for eval. `--global` persists the active subos plus the symlink.
- keeper: `--no-keep` off; `--keep` never expires (until `subos stop`); `--ttl` sets a custom idle TTL. Automatic default = storage in {image,tmpfs} + sandbox + Linux -> on, TTL 5 minutes.
- `--gpu` is opt-in NVIDIA + DRM passthrough, **bwrap only**; missing devices are skipped silently; **ignored under proot**. Backend selection: bwrap first -> userns probe -> proot fallback, and **the system `/usr/bin/bwrap` is skipped**; proot **cannot stop a ptrace escape** (the docs say so explicitly). `XLINGS_SUBOS_MODE=sandbox` exists to **refuse nested entry**.

```bash
xlings self doctor [--deep] [--scope <PACKAGE[@VERSION]>] [--subos <NAME>] \
                   [--fix] [--dry-run] [--show-ok] [--reset-metadata]
```
**`self doctor`**: read-only by default, checking workspace / version DB / shim table / payload / sysroot / subos state. Commands printed after `-> run` in the report **are guaranteed to be runnable verbatim** — prose moved to a separate `remedyNote` line in 2026.9.3.2 [doctor.cppm:341-345] and install suggestions are resolved through `xvm::recorded_owner` into a real package coordinate, falling back to `xlings search <name>` rather than guessing (on a real home 218 of 338 program names are not package names, so `xlings install g++` simply does not run). `--fix` **implies `--deep`** and runs four phases: cheap metadata repairs -> payload ladder -> residue after reload -> another round of cheap repairs; **it re-examines after fixing and reports the post-fix state**.
**Flags that changed in 2026.9.12.1** — see `references/version-notes.md`:
- `--show-ok` is the current name; **`--all` still works but warns once per run** and will stop being documented [src/core/xself.cpp:157-166]. Change your scripts, or eat a warning line on every invocation.
- `--subos <NAME>` anchors the **whole process** (both `XLINGS_ACTIVE_SUBOS` and the in-process override, so spawned subcommands follow); an unknown name **exits 2** [doctor.cpp:5047-5074].
- `--fix` **no longer stops at the current subos**: for every other subos that owns a finding it spawns `<client> self doctor --fix --subos <name>`; a child carrying `--subos` does not recurse further. Each child is bounded by **`XLINGS_DOCTOR_CHILD_TIMEOUT`** seconds (default **1800**, `0` = wait forever) [doctor.cpp:3220-3237] — **but only where `timeout(1)` is on PATH** (checked once per process, `:3249-3255`): on Windows, stock macOS and minimal containers there is no bound at all and a stuck child hangs the parent. Bring your own `timeout` there. A failed child counts as outstanding, suppresses the `verifiedBy` stamp, and makes the parent exit non-zero.
  => **Budget for this before you run it.** `--fix` implies `--deep` (upstream measured `--fix --dry-run` at 148-191s on a 124-package / 71 GB home) and that cost is now multiplied by the number of affected subos, with children free to download and reinstall. Run `--fix --dry-run` first, and keep whatever CPU/IO throttle your machine needs on the whole command — children inherit `nice`, but not per-command variables you set for a build tool.
**Exit codes**: `0` = converged with nothing outstanding; `1` = issues, outstanding items, or a regression remain; `2` = bad input (`--subos` naming a subos that does not exist, `--scope` without `--deep|--fix`).
**Read the verdict line, not only `$?`** [doctor.cpp:4949-4985]: a `--fix` that cleaned up by dropping registrations or deleting sysroot links prints `status  N registration(s) dropped and M sysroot link(s) removed — nothing here could restore them; the rest of the home is consistent` and **still exits 0**, deliberately, because the exit code answers "does this home still need a human". Only a genuinely lossless run prints `OK — workspace, shims, and payloads are all consistent`.
**What `--fix` explicitly does not do**: it does not re-patch ELF (1.7); it does not fix `SubosRuntimeDrift` (declaration vs what the sysroot actually serves — **reported, never fixed**, because which side is the accident cannot be determined from here); it does not fix `InterpRuntimeDrift` (Notice only, no exit-code change); it does not fix `SubosEnvConflict`; it does not fix `ForeignPayload` (fixing it would mean adopting a package on the user's behalf); it does not fix `UnverifiedPayload` (29 on a real machine, all graphics stack; "guessing" does not solve it). **Packages and payloads themselves are never deleted by `--fix`**; `--reset-metadata` is a separate switch because **it loses information**.
WARNING: when `.xlings.json` is **not valid JSON**, `--fix` **refuses to touch it** (rewriting would discard a workspace nobody can parse) and the remedy becomes `inspect <path>`.
WARNING: the per-finding remedy for `ForeignPayload` still prints `xlings subos use X && xlings self doctor --fix` [doctor.cpp:1365] even though `--fix --subos X` is now the shorter route. Upstream has this on its own follow-up list; the printed line works, it is just one command longer than it needs to be.
**One new finding is worth a deliberate pass after upgrading**: `SweptPayload` (2026.9.14.1, Error level) marks install directories that absorbed other packages' archives and sidecars under the old shared-staging behaviour. `--fix` repairs it by **remove-then-install**, skipping the cheap "just install" rung because a swept payload already reads as correctly installed [doctor.cppm:263-273]. The install-layout contract behind it is in §10; the measured damage and how to check for it are in `references/version-notes.md`.

## 8. Machine-readable output (four layers, CI/agent integration)

| Layer | Trigger | Shape |
|---|---|---|
| global plain text | any command + `--agent` | ANSI off, TUI layout off; error/warn -> stderr, everything else -> stdout |
| single-command JSON | **`xlings index list --json`** (the only `--json`) | array, indent 2 |
| NDJSON protocol | `xlings interface [capability]` | one JSON object per line, protocol **v1.0**, **20 capabilities** |
| command tree JSON | `xlings --command-reference-json` (**hidden**, must be the only argument) | the whole command tree |

`--agent` and `interface` **are not equivalent**: `--agent` does **not** set `tui_mode(true)`, logs still go to the terminal, and it only removes ANSI decoration; **`interface` is the fully programmatic channel**.
**A bare `xlings interface` does not return the capability table**: it returns `{"kind":"result","exitCode":1,"error":"capability name required. Use --list…"}` and **exits 1**. Getting the table requires `--list`, and the key is **`protocol_version`**, not `protocol`. Inputs use `--args <JSON>` or `--args-file <PATH>` (the latter avoids Windows cmd.exe quoting problems). Full set of event `kind`s: `progress`/`log`/`data`/`prompt`/`error`/`result`/`heartbeat`. The **stdin control channel** takes one JSON object per line with key `action` in `cancel`/`pause`/`resume`/`prompt-reply`.
- **Parameters are validated before dispatch (2026.9.20.1, #464, `docs/spec/interface-ndjson-v1.md` §3.3.1)**: for **every** capability, `--args` that is not valid JSON or not a JSON object is refused; for capabilities that declare `inputSchema.required` (12 of the 20), a missing or `null` required field is refused. Either way the server emits `{"kind":"error","code":"E_INVALID_INPUT","message":"missing required field(s): …","hint":…}` then `{"kind":"result","exitCode":1}` and **does not run the capability** [src/interface.cpp:126]. `--args ""` still means `{}`; unknown extra fields are still accepted (this is not full JSON Schema validation).
  WARNING, why it matters: before 2026.9.20.1 a misspelled `plan_install` field returned `{"exitCode":0}` - byte-identical to "nothing to install" - and a malformed `update_packages` / `list_packages` silently fell back to "everything". Worse, `create_subos --args '{}'` registered a SubOS named `""` whose directory is the SubOS **root**, and `remove_subos --args '{}'` then deleted every SubOS in the home, both reporting success (#611). From 2026.9.20.1 `subos::create` / `subos::remove` also refuse an empty name themselves [src/core/subos.cpp:541]. **On an older xlings, never send a capability an empty or partial params object.**
- Extraction failures carry their kind since 2026.9.20.1 (#376): a corrupt archive or unsupported entry is `E_INVALID_INPUT` (the hint says the cache was cleared and a retry re-downloads), a write failure is `E_DISK_FULL`; both used to be `E_INTERNAL`.
- `list_repos` entries gained `artifact_bases[]{region,url}` (2026.9.16.1), in the order the refresh will try them.
- CLI and capability are **not one-to-one**: `plan_install` (dry-run), `list_subos_shims`, `env`, `system_status`, `list_repos`/`add_repo`/`remove_repo` have **no equivalent standalone CLI subcommand**.
- WARNING, **breaking field rename in 2026.9.3.1**: `list_subos` entries no longer carry `pkgCount`. They carry **`commands`** (the size of the routing table, i.e. how many command names the subos publishes) and **`packages`** (releases, de-duplicated by `bindingGroup` — one llvm is 1 package and roughly 40 commands) [src/capabilities.cpp:303-304; src/core/subos.cppm:60,64]. The read side still falls back to an old `pkgCount`, but anything that parses the output must be updated; the agent text likewise went from `(N packages)` to `(N commands, M packages)`. The upside is that `packages` is finally a real package count and can be asserted on in a gate.
- WARNING, **the 2026.9.12.1 verbs have no capability parity**: `remove --all/--all-subos/--subos`, `config --list-xpkg/--remove-xpkg/--clear-xpkg` and `self doctor --subos/--show-ok` are **CLI-only**; the NDJSON channel got only the `list_subos` field rename. If you drive xlings through `interface` rather than argv, those operations are simply not reachable yet (upstream openxlings/xlings#593, **still open on 2026-09-23**).
- WARNING: `docs/spec/interface-ndjson-v1.md:197-215` **lists only 19 while the code has 20** (missing `list_index_versions`). **Do not copy that passage from upstream docs.**
- Reference clients live in `examples/clients/` (bash+jq / python / node); their README notes that they **do not cover** streaming `install_packages`, the stdin control channel, or `run`/`exec` (deferred to v2). Full tables and fields in `references/machine-output.md`.

## 9. Integration with mcpp

- **Bootstrap cycle**: xlings **is built by mcpp**, mcpp **is installed by xlings**; the cycle is broken by `workspace.mcpp` in `.xlings.json` (CI runs `xlings install -y` first, then `mcpp build`).
- **`MCPP_VENDORED_XLINGS` has three effect sites; only the first is cross-platform**: (1) **first in the acquisition chain** — if present it is `copy_file`d to `destBin` with the exec bit set [mcpp/src/fallback/xlings_binary.cppm:107 at mcpp 2026.9.15.2] (since mcpp **2026.9.17.2** the second rung is the xlings released beside the running mcpp, `<prefix>/registry/bin/xlings`, and `which xlings` is third - before, an mcpp installed as an xlings package fell through to whatever xlings was on PATH, even one older than its pin); (2) candidate version probing (`:219`); (3) direct runtime use on Windows [mcpp/src/config.cppm:124-128] (the copied xlings inside the sandbox may misbehave when installing large packages because it lacks a complete runtime; `XLINGS_HOME` still guarantees packages land in the mcpp sandbox). Version floor: replacement is only considered when the vendored one is **strictly older** than the pin, and **only after checking that the candidate really is newer** (skipping that check once downgraded 2026.8.2.1 to a system 0.4.51).
- **mcpp never reads `XLINGS_HOME`** (zero hits for `getenv("XLINGS...")` in its tree); it **always passes it explicitly**. The home is computed: `MCPP_HOME` is resolved in [mcpp/src/home.cppm] and `registryDir = mcppHome/"registry"` is declared at [mcpp/src/config.cppm:67], assigned at [`:618`]; overridable by `[xlings] home` in `config.toml`.
- **`[xlings] deps` provisions into `$MCPP_HOME/registry`, and a `subos` declaration cannot change that.** Before #531, `deps` was **written to a file and stopped there** (`deps = ["xim:mesa"]` produced a file mentioning mesa, no project SubOS, and then `fatal error: gbm.h: No such file or directory`). Now the first build really installs, via the `interface install_packages` NDJSON protocol (progress callbacks, subprocess errors captured, stdin sealed). WARNING: it is **GLOBAL scope, and that is the point** — the obvious alternative (calling `install_packages` against the project env) **was measured not to work**: headers land in `<proj>/.mcpp/.xlings/subos/_/usr/include` while `--sysroot` points at `$MCPP_HOME/registry/subos/default`, two SubOS views, with the payload in the one the compiler does not read. => **Even when the project declares `subos = "tools"`, `[xlings] deps` still installs into `registry/subos/default`.** Idempotency is **by content**, and **the stamp has moved out of the project**: it now lives at **`$MCPP_HOME/provisioned/xlings-deps-<16 hex FNV-1a of the dep list>`** [mcpp/src/build/prepare.cppm:1469-1484], keyed by the **list** rather than by the project, because the installation is shared and two projects declaring the same packages should pay for it once. The old `<project>/.mcpp/.xlings-deps.stamp` is still **read** as a legacy fallback but never written [`:1517`]. The reason is worth keeping: the stamp records a global effect, so a stamp inside the project made a project claim packages were installed after `MCPP_HOME` was wiped or replaced, and `mcpp clean` (which removes `target/`, never `.mcpp/`) could not clear it. **Ordering is load-bearing** — provisioning must run **before** runtime binding resolution; and it **deliberately excludes `penv.deps`** (the cross-compilation target sysroot is inferred by mcpp, not declared by the author, and provisioning it would turn working builds into hard failures).
- **`[xlings]` subkeys map 1:1 onto xlings' own `.xlings.json` schema and are written through verbatim** to `<proj>/.mcpp/.xlings.json`, **with no translation layer**.
- **The two homes are fully independent and never read or write each other**: the mcpp sandbox's `$MCPP_HOME/registry/.xlings.json` lists only `mcpplibs` (**deliberately** — xlings adds its own defaults such as `xim`, and listing them explicitly would cause cross-index name collisions during dependency resolution, e.g. `linux-headers` exists in both scode and xim); `mirror` is hard-written `"auto"` and `lang` hard-written `"en"`. WARNING: **`"auto"` is not a first-class xlings value** — no xlings code or test recognizes it, and it works purely because every consumer falls back to GLOBAL. Net effect = "GLOBAL first + CN as a cross-region candidate + adaptive latency reordering". The mcpp comment says this replaced a historically hard-coded `"CN"` (which **forced** CN and **disabled** adaptive): "mirror selection is xlings' job; mcpp merely declines to override it by default."
  Since mcpp 2026.9.16.1 the `mcpplibs` entry it writes carries `artifact = { GLOBAL = github.com/xlings-res/mcpp-index, CN = gitcode.com/xlings-res/mcpp-index }` (existing registries are upgraded in place), and the xlings mcpp bundles from 2026.9.16.2 reads that as the ordered chain of §5.1 - so under `mirror = CN` a GitCode failure goes to the GitHub artifact before any git clone.
- WARNING: `mcpp self config --mirror` **validates more strictly than xlings itself** (`foo` -> exit 2) and is **two-phase**: `--mirror` given and MCPP_HOME brand new -> **seed**; already initialized -> skip seeding and shell out to `xlings config --mirror`.
- **Fixed in 2026.9.20.1: an install that emptied the shared shim directory** (openxlings/xlings#582 / #604, closed 2026-09-20). The mechanism was not mcpp-specific: inside a **project** scope, the "which SubOS is the global one" question was answered by "which SubOS does this command act on", so the global workspace read as empty and the derived shim table removed every global entry - `mcpp`, `gcc`, `cmake`, `ldd` and the rest (upstream measured 172 routing entries lost on one home, and traced every red `fresh-install (core)` CI cell - red since at least 2026-09-12 - to the same cause, introduced when the table became derived in 2026.9.3.1). The fix is one answerer for "the global SubOS" (`Config::global_subos_name_()`) plus a rule that an **unreadable** workspace is not an empty one: `sync_shim_tables` refuses to rebuild from an unobserved scope and says why.
  - On a client **older than 2026.9.20.1** (including the 2026.9.16.1 that mcpp 2026.9.21.3 bundles), `mcpp: command not found` right after an `xlings install` is still this side effect, not a broken install; `xlings install xim:mcpp@<version>` restores the names.
  - A home damaged by an older client is repaired by any global-scope `install` / `use`, by `xlings self init`, or by `xlings self update` (it runs the install path); read-only commands leave it as is. `self init` prints `routing table: +N -M shim(s)` when it repaired something and is silent on a second run.
- **mcpp reads SubOS but never creates one**: a name that does not resolve is a **hard error**, with no fallback to default/active. Existing but without a `subos_info` block -> **degrade rather than fail** (runtime binding reports `inconclusive`, a note is printed, the build continues). WARNING: mcpp's own sandbox subos was measured to be in exactly this state — **356 workspace records, zero self-description** [mcpp/src/xlings/subos_info.cppm:32].

## 10. Boundary between the two indexes (xim-pkgindex vs mcpp-index)

**One-line test (zero crossover over 187 + 175 files)**: a descriptor with **`function config()` + `xvm.add`** -> **xim-pkgindex**; one with **`mcpp = {}` or `namespace`** -> **mcpp-index**.

| Dimension | xim-pkgindex (187 .lua, `origin/main @ 99bdba3`) | mcpp-index (175 .lua, `origin/main @ fb4b324`) |
|---|---|---|
| `package.namespace` | **9/187** declare it; the rest inherit the index repo name `xim` | **175/175 declare explicitly** |
| `mcpp = {}` block | **0/187** | most have one; Form A omits it deliberately and uses the upstream `mcpp.toml` |
| lifecycle hooks | **179/187 define one** (the 8 exceptions are 7 `type = "script"` + 1 `type = "template"`, which carry `xpkg_main`; the 186/187 figure is a different fingerprint — recipes that `import("xim.libxpkg…")`) | **16/175**, all "external build system" cases (the whole `compat.x11`/`compat.xcb`/graphics-stack cluster plus `compat.openssl`, `compat.openblas`, `compat.ftxui`, `compat.eui-neo`) |
| `xvm` usage | pervasive; tests force `config()` to call `xvm.add(package.name)` | **0/175** |
| `spec` | 117x`"1"` + 70x`"2"` | **175x`"1"`**, zero V2 |
| `xpm` contents | platform/arch-specific **prebuilt binaries**, three different platform URLs | **source archives**, all three platform URLs and sha256 **byte-identical** |
| CN mirror org | `gitcode.com/xlings-res` | `gitcode.com/mcpp-res` |
| client version contract | **no `min_xlings`** | has `index.toml`: `min_mcpp`/`latest_mcpp` |

- **Test**: the deliverable is a **built artifact** (binary/toolchain/font/driver/script/config), acquired with `xlings install`, lands in PATH/sysroot/xvm, needs hooks, varies by OS x arch -> **xim**; the deliverable is **a library to link into a C++23 project**, acquired with `mcpp add`, no hooks, and `xpm` holds a source archive -> **mcpp-index**.
- **Grey zone** (`ffmpeg`/`opencv`/`vulkan`/the X11 family) is split **by consumer**: the xim side is "runtime/tool binaries" (`xim:mesa` provides `libGL`), the mcpp side is "libraries linkable at compile time" (`compat.glx-runtime`). Same name, different thing, disambiguated by namespace.
- **Hard boundary given by the routing code** [mcpp/src/pm/index_route.cppm:18-27,127-140]: `authoritative_for()` may "say it does not exist" only for four identities — `mcpplibs`/`mcpplibs.*`/`compat`/no namespace. **`xim:` falls outside its identity rules, so not finding it does not mean it does not exist**; callers must fall through rather than fail hard.
- **Shared between the two indexes**: the same grammar, **the same payload store** (measured: `xim-x-gcc` coexists with `compat-x-zlib` and `nlohmann-x-json`), the same install engine, the same mirror table shape. **Not shared**: the semantics of the `mcpp` section and V2's multi-architecture dimension.
- **The install layout of a hookless package is now specified** (2026.9.14.1, `docs/spec/xpkg-manifest-v1.md:158`): for a package that is neither `type = "subos"` nor defines `install()`, the installer runs no code to place files — `pkginfo.install_dir()` receives **exactly the entries of that package's own archive, laid out the way the archive lays them out, with the top-level directory kept, and nothing else**; the archive itself stays in the download cache and is never moved in. Descriptors that point at a path inside the extracted tree (`"*/…/mcpp.toml"` and friends) depend on that kept top-level directory — it is now spec rather than an implementation accident, so you can write against it. A package **with** an `install()` hook still extracts beside its archive; that is the hook's contract.
- **Full SOP for writing an xim package** -> `references/xim-packaging.md` (new packages use `spec = "2"`; `res = true` is legacy). V1/V2 differences and `ArchEvidence` -> `references/config-layout.md`. **Writing an mcpp-index package** -> the `mcpp` skill's `references/packaging.md`.

## 11. Isolation and gate recipes (project-local home)

- **Commands that go through mcpp** with a project-local home: `env -u XLINGS_HOME -u XLINGS_BIN MCPP_HOME="$PWD/.mcpp" .mcpp/bin/mcpp …`. Honest labelling: both `-u` are **formalities as far as mcpp is concerned** — it never reads `XLINGS_BIN` (zero read points) and never reads `XLINGS_HOME` (it sets it explicitly every time). The thing that actually isolates is **`MCPP_HOME`**. Keep them as defensive discipline (an `xlings` on PATH and the login shell's profile can still bleed in), not because mcpp requires them.
- **Bare `xlings`** against an isolated home requires the five-part strip plus a clean CWD:
  ```bash
  cd /tmp/clean-cwd    # or any directory with no .xlings.json above it
  env -u XLINGS_HOME -u XLINGS_BIN -u XLINGS_PROJECT_DIR -u XLINGS_ACTIVE_SUBOS \
      -u MCPP_VENDORED_XLINGS XLINGS_HOME="$W/xlings-home" "$W/bin/xlings" …
  ```
- **CWD discipline** (1.2b): before trusting the strip, check every level from cwd up to `/` for a `.xlings.json`. Note that the xlings source checkout itself carries one (`projectScope:false`, which still leaves its `workspace` key readable by a bare `xlings install`) — be careful when running inside that tree.
- **Two variables that are often mislabelled in copied command lines**: `MCPP_VENDORED_XLINGS=<registry>/bin/xlings` is a **deliberate setting** (make mcpp use the xlings inside that registry) — not residue, do not delete it. `MCPP_INDEX_MIRROR=GLOBAL` is a **no-op on both sides**: zero hits in the mcpp tree, and on the xlings side the only mirror variables are `XLINGS_INSTALL_MIRROR`/`XLINGS_MIRROR`/`XLINGS_RELEASE_MIRROR`, read **only by `self install`** (1.4). => It can be dropped from any command line that carries it.
- **For a hard guarantee of "never touch the global environment"**: stripping the environment is not enough; either change `HOME`, or confirm the `$HOME` fallback in 1.2a cannot be triggered.
- **Side effect of a shared home**: when building an external project under the same `MCPP_HOME`, mcpp installs gcc into the shared home and makes it the default because that project pins no toolchain. A project that pins its own toolchain does not consume that default. [field-tested 2026-08-29]
