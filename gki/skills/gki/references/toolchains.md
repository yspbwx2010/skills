# Toolchains and the module build command

## 1. Use the kernel branch's toolchain

Build the kernel and every module with the clang prebuilt pinned by the **ACK kernel branch**, not the
clang listed in the AOSP platform (userspace) release tables. The branch pins it in
`build.config.constants` (`CLANG_VERSION=r510928` for `android15-6.6`).

| ACK branch | Clang | LLVM | Kernel-build prebuilts branch |
|---|---|---|---|
| android12-5.10 | r416183b | 12.0.5 | master-kernel-build-2021 |
| android13-5.10 / 5.15 | r450784e | 14.0.7 | master-kernel-build-2022 |
| android14-5.15 / 6.1 | r487747c | 17.0.2 | main-kernel-build-2023 |
| android15-6.6 | r510928 | 18.0.0 | main-kernel-build-2024 |
| android16-6.12 | r536225 | 19.0.1 | main-kernel-2025 |

This is a baseline verified when written, not a permanent mapping: confirm with the branch's
`build.config.constants`. A `clang-rNNNNNN` directory missing from a prebuilts branch tip may still exist
at an older ref of that branch.

Check what a build actually used:

```sh
grep -E 'CC_VERSION_TEXT|CLANG_VERSION|LLD_VERSION|PAHOLE_VERSION' "$KERNEL_OUT"/.config
# CONFIG_CC_VERSION_TEXT="Android (...) based on r510928) clang version 18.0.0 (...)"
```

An `M=` build with a different compiler prints
`warning: the compiler differs from the one used to build the kernel`. Treat it as an error: flags,
KCFI hashing and code generation can differ.

## 2. The module build command

```sh
make -C "$KERNEL_SRC" O="$KERNEL_OUT" ARCH=arm64 LLVM=1 LLVM_IAS=1 \
     KCFLAGS=-D__ANDROID_COMMON_KERNEL__ M="$PWD" modules
```

- `KERNEL_OUT` must be the output of a **full** build (`.config` plus a complete `Module.symvers`).
  `make Image` alone does not produce a complete `Module.symvers`; build `modules` too.
- `LLVM=1` selects clang, ld.lld and the LLVM binutils; `LLVM_IAS=1` the integrated assembler. `LLVM=1`
  takes the tools from `PATH`: put the branch's `clang-rNNNNNN/bin` first, or pass
  `LLVM=/path/to/clang-rNNNNNN/bin/` (trailing slash).
- `KCFLAGS=-D__ANDROID_COMMON_KERNEL__` matches what `build.config.common` passes for ACK builds.
- Add `-j"$(nproc)"` as needed. Output is an **unsigned** `.ko`
  ([symbols-and-signing.md](symbols-and-signing.md) section 2.4).

## 3. Flags the kernel Makefiles add themselves

Never add these by hand, and never strip them from your module (for example with `ccflags-remove-y`):

| Flag | Added by | When |
|---|---|---|
| `-fsanitize=kcfi` | top-level `Makefile` | `CONFIG_CFI_CLANG=y` |
| `-ffixed-x18` | `arch/arm64/Makefile` | `CONFIG_SHADOW_CALL_STACK=y` |
| `-fsanitize=shadow-call-stack` | top-level `Makefile` | SCS **without** `CONFIG_DYNAMIC_SCS` |
| `-mbranch-protection=pac-ret` + `-fasynchronous-unwind-tables` | `arch/arm64/Makefile` | pointer auth / `CONFIG_UNWIND_TABLES` (the dynamic-SCS case of this build) |
| `-Werror` | `scripts/Makefile.extrawarn` | `CONFIG_WERROR=y` (set in this build) |
| `-Werror=incompatible-pointer-types`, `-Werror=implicit-function-declaration`, `-Werror=strict-prototypes`, ... | `scripts/Makefile.extrawarn` | always |

All of them reach `M=` external builds. A module built without `-fsanitize=kcfi` has callbacks without
type hashes, and the kernel's first indirect call into one traps (inferred). See [cfi.md](cfi.md).

## 4. Rust

Whether Rust is needed or possible depends on `CONFIG_RUST`, not on the kernel version ("6.12+" is not
the rule).

- In this `android15-6.6` `gki_defconfig` build `CONFIG_RUST` cannot be enabled: `init/Kconfig` has
  `config RUST` depend on `!MODVERSIONS` and `!SHADOW_CALL_STACK` (both are `y`), and the ACK top-level
  `Makefile` stops with `Enabling Rust and CFI silently changes the KMI.` if `CONFIG_RUST` and
  `CONFIG_CFI_CLANG` are both set.
- `CONFIG_RUST_IS_AVAILABLE=y` only means a usable `rustc` was found; it does not enable Rust.
- When a branch does use Rust, use the Rust prebuilt that branch pins, like clang.

## 5. Other toolchain traps

- `CONFIG_DEBUG_INFO_BTF=y` and `CONFIG_DEBUG_INFO_BTF_MODULES=y`: module BTF is generated by pahole
  against the kernel's BTF. Use the same pahole as the kernel build (`CONFIG_PAHOLE_VERSION=131` here); a
  different pahole changes BTF output. `CONFIG_MODULE_ALLOW_BTF_MISMATCH=y` in this build, so a mismatch
  drops the module's BTF instead of refusing the load.
- Prebuilt build-tools on `PATH` do not make a build hermetic: they ship no complete glibc sysroot, and
  host tools still come from the machine.
- The kernel clang is not an Android userspace toolchain. Build Android userspace ELF binaries with the
  NDK (Bionic).
